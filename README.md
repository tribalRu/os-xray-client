# os-xray-client for OPNsense 26.x

Full-featured Xray-core client plugin for OPNsense with native `tun` interface support, `vless://` / `trojan://` / `ss://` link parser (vless, vmess, trojan, ss, hysteria2), routing rules editor, latency/traffic monitoring, GeoIP/GeoSite updater, and GitHub self-update.

## Requirements

- OPNsense 26.1 (amd64 or aarch64)
- Root shell access on the firewall
- The installer downloads Xray-core + GeoData from GitHub on first install

## Quick Install on OPNsense

Run the following command in the OPNsense root shell:

```sh
fetch -o /tmp/main.tar.gz https://github.com/tribalRu/os-xray-client/archive/refs/heads/main.tar.gz && tar -xzf /tmp/main.tar.gz -C /tmp && sh /tmp/os-xray-client-main/install.sh
```

Then open **VPN > Xray Client**, configure nodes/rules under **General**, and click **Apply & Restart Xray**.

## TUN (`Variant A`) — transparent L3 routing

Xray-core **creates the TUN interface itself** while the service runs (FreeBSD `tun(4)`); it does not exist otherwise, and the plugin deliberately never pre-creates it (a pre-created interface makes Xray fail with `interface already exists`).

1. In **General > TUN Interface**, enable *Enable Native TUN Inbound* (default interface `tun_xray0`; the name must start with `tun_`, because OPNsense does not see TUN interfaces named otherwise; gateway prefix `10.255.0.1/30`, MTU `1500`).
   - `TUN Tunnel Subnet` is the **gateway prefix** Xray uses for the tunnel: Xray keeps the gateway address (`10.255.0.1`) as the in-tunnel endpoint and assigns the next address to the interface (`10.255.0.2` for a `/30`). CIDR must be `1..31` so a local address exists inside the prefix.
2. Click **Apply & Restart Xray**. The prestart hook removes a stale interface left by an older plugin version / an unclean Xray crash, then Xray creates `tun_xray0` itself.
3. Assign it under **Interfaces > Assignments**, save, enable it (e.g. `opt5`), and create a gateway pointing at `10.255.0.1` **with gateway monitoring disabled** (the far end has no real host to ping).
4. Add a LAN firewall rule that routes selected (or all) traffic to that gateway (Firewall > Rules > LAN > Advanced > Gateway).
5. To use domain rules (`geosite:ru`, …) keep *Enable Domain Sniffing* on.
6. Traffic is decided per connection by Xray's routing rules (`node_<uuid>` / `direct` / `block`); `direct` traffic exits via the normal WAN route.

Full-tunnel auto-routing (`autoSystemRoutingTable`, which replaces the system routing table and binds outbounds to a physical interface via a second FIB) is not wired up yet: on FreeBSD it requires `net.fibs=2` in `/boot/loader.conf` and a reboot. Manual policy routing above works out of the box.

The prestart/poststop hooks honour `enable_tun` and clean up stale interfaces automatically.

### Troubleshooting: pages on LAN clients never leave SYN_SENT, Xray sees nothing (empty access.log)

If the wall/client can ping `192.168.1.199` but cannot open any website, and `netstat -i -I tun_xray0` shows `Ipkts: 0` while pf shows the rule passing packets (`pfctl -sr -v | grep route-to` → non-zero `Packets`), the gateway for the policy rule is pointing at the wrong end of the tunnel.

The gateway must be the **Xray end** of the `/30` (`10.255.0.1` for the default prefix), **not** the address assigned to `opt1` by OPNsense (`10.255.0.2`). Pointing the gateway at `10.255.0.2` makes pf try to route into the wall’s own interface address and silently drop every packet — no error message is produced anywhere and Xray never sees a single packet.

Fix: System → Gateways → Configuration → edit the `XRAY_GW` → *Gateway address* = `10.255.0.1` → Apply → `pfctl -F states` to drop stale SYN_SENT states.

## Outbound protocols

The node dialog supports every outbound protocol implemented by Xray-core. Choosing a protocol shows only its relevant fields:

| Protocol | Authentication / key fields | Transport |
| --- | --- | --- |
| VLESS | UUID, encryption, XTLS flow | RAW, WS, gRPC, XHTTP, HTTPUpgrade + TLS/REALITY; XDRIVE (VLESS only) |
| VMess | UUID, encryption (`auto`/AES/ChaCha20), experiments | RAW, WS, gRPC, XHTTP, HTTPUpgrade + TLS/REALITY |
| Trojan | password | RAW, WS, gRPC, XHTTP, HTTPUpgrade + TLS/REALITY |
| Shadowsocks | cipher + password (2022 keys must be base64) | RAW, WS, gRPC, XHTTP, HTTPUpgrade + TLS/REALITY |
| SOCKS 5 | username / password (optional) | RAW, WS, gRPC, XHTTP, HTTPUpgrade + TLS/REALITY |
| HTTP | username / password, extra headers | RAW, WS, gRPC, XHTTP, HTTPUpgrade + TLS/REALITY |
| WireGuard | private/public keys, PSK, endpoint, allowed IPs, MTU, reserved bytes, remote DNS | native UDP tunnel |
| Hysteria 2 | auth password, UDP idle timeout | QUIC + mandatory TLS |
| MASQUE | username / password, authority, path, headers, remote DNS | HTTP/2 or HTTP/3 + mandatory TLS |
| Freedom | redirect, PROXY protocol, final rules | none |
| Blackhole | response (`none` or HTTP 403) | none |
| DNS | transport/address/port rewrite, rule list | none |
| Loopback | inbound tag used when re-entering routing | none |

Protocol-specific fields, the Transport section, Mux.Cool and the custom `streamSettings` override are shown/hidden dynamically. All generated configs are accepted by `xray run -test` (checked against Xray-core 26.11.9).

## Notes

- **Raw JSON mode**: paste a complete Xray config into *Raw Xray JSON*; it's validated (`json_decode`) and tested (`xray run -test`) before restart. In UI mode the template escapes all string values (`tojson`), so quotes in names/addresses won't break `config.json`.
- **Advanced Mode**: General → *Show Expert Config Tab* (formerly *Advanced Mode*) shows an extra **Expert Config** tab with the exact `/usr/local/etc/xray/config.json` Xray runs. This is all it controls — it does **not** touch the advanced fields. Hiding/showing advanced rows is a separate, per-screen choice (**Show advanced fields** in the node dialog and in General Settings, **Show additional conditions** in the rule dialog), persisted in browser storage. View the Expert Config tab read-only or edit it manually; saving validates (`xray run -test`), backs up the previous file (`config.json.bak-*`), switches the plugin to Raw JSON mode and restarts Xray. The UI builder no longer regenerates the file until you switch back.
- **Routing rules**: the list shows a single **Match** column with every condition of a rule (domains, IPs, ports, sniffed protocol, inbound, source, users) and flags duplicate sequence numbers; a new rule is appended after the last one. The dialog is ordered Rule → Match traffic by → Additional conditions; the rarely used conditions (inbound tags, source IPs/ports, users, rule tag) sit behind **Show additional conditions** and open automatically for a rule that already uses one. Reordering is done with the ↑/↓ buttons in the Actions column (rules renumber automatically to 10/20/30…). Adding from dialog offers built-in presets (bypass LAN/private, bypass RU domains/IPs, block ads); "geosite:ru"-style tags need the matching GeoData preset. In the Target Outbound Action field pick a built-in outbound (`direct`, `block`), a node (`node_<uuid>`, stable across add/remove/reorder) or a **balancer** by its tag. Rules can also match on **Inbound Tags** (`tun-in`/`socks-in`/`http-in`/`api-in`), **Source IPs/Subnets** (`192.168.0.0/16`, `geoip:private`, `!geoip:ru` — only for traffic that reaches Xray with the client address, e.g. TUN; behind NAT everyone looks identical), **Source Ports**, **Auth Users** (SOCKS/HTTP auth users) and an optional **Rule Tag** (used in Xray's stats); empty fields are ignored. The **Routing Policy** section sets `routing.domainStrategy`: `IPIfNonMatch` (default — resolve only domains that matched no rule before IP matching), `IPOnDemand` (resolve only when an IP rule needs it) or `AsIs` (never resolve, cheapest, leaks nothing).
- **TUN interface**: Xray creates the TUN inbound itself (no manual ifconfig needed). A second **TUN IPv6 Subnet** field can add an IPv6 `/64` prefix (e.g. `fd00::1/64`) to the same interface — parsed fine on Linux/macOS; on FreeBSD the interface gets its link-local IPv6 automatically and the field is mostly formal. The **Outbound Interface Binding** field (`tun_auto_outbounds_interface`) binds Xray's outbound sockets to a physical interface (or `auto`) so outbound traffic never loops back into the TUN — on FreeBSD this requires `net.fibs=2` in `/boot/loader.conf` and a reboot first; with the default `net.fibs=1` Xray refuses to start and Apply/Restart is rejected, which is the safe default.
- **Local SOCKS5 / HTTP proxies**: the local proxies in **General Settings > Local Proxy Ports** (SOCKS5 / HTTP) can now require authentication (`SOCKS5` / `HTTP Proxy Authentication`: noauth or password). The HTTP proxy has its own **Listen IP Address** (`http_listen`, falls back to the SOCKS listen address; the upgrade migration copies `socks_listen` into it, so existing setups are unchanged). When binding the proxies to LAN, also enable authentication - the help text spells this out. Child rows shown under a proxy are hidden while the proxy itself is disabled (with *Enable Local HTTP Proxy* off, Listen IP / Authentication / Port and its username/password disappear; they all re-appear when the proxy is re-enabled). The username/password rows additionally disappear in noauth mode, and password mode requires both fields to be filled. The same hide-when-off rule applies to the TUN section (*Enable Native TUN*), *Domain Sniffing*, *Automatic Latency & Traffic Telemetry*, *Built-in DNS* and *Load Balancer Observatory* - nothing is shown where it would have no effect.
- **Domain sniffing**: **General Settings → Domain Sniffing Options** controls which types are sniffed (HTTP, TLS/HTTPS, QUIC/HTTP3, FakeDNS), the `routeOnly` toggle and a `domainsExcluded` list that skips sniffing for specific domain rules (e.g. `geosite:category-ads-all`). All inbounds (`tun-in`, `socks-in`, `http-in`) share these settings.
- **Load balancing**: the **Balancers** tab groups nodes by tag prefix (`node_` covers every node) and picks one per connection with `random`, `roundRobin`, `leastPing` or `leastLoad`; an optional `fallbackTag` (empty by default, so traffic fails closed instead of leaking through `direct`) is used when the selector matches nothing usable or every probe fails and an observatory is enabled. A rule that targets a balancer tag is rendered as `balancerTag` instead of `outboundTag`. `leastPing`/`leastLoad` need the observatory in **Balancers → Load Balancer Observatory** (below the balancers table) (burst - recommended - or background; URL, interval, sampling, timeout). With two nodes at different latencies `leastPing` follows the faster one and switches when it fails. **Show live selection** asks the Xray RoutingService (`xray api bi`) which outbound the balancer currently selects and prints it inline with node names — a fast sanity check after every `leastPing` flip, no need to dig into logs.
- **Logging**: **General Settings → Enable Access Log** (off by default) writes the proxied connection list to `/var/log/xray/access.log`. **Enable DNS Log** additionally logs every DNS query the built-in DNS server handles — useful when a domain silently fails to resolve. **Mask IP Addresses in Logs** (e.g. `10.0.0.0/8`) masks matching octets of IPs in the logs, useful when sharing logs. Logs are available via the main menu under **VPN → Xray Client**, like the Firewall logs viewer: **Error Log** (`/ui/diagnostics/log/xray/error`) and **Access Log** (`/ui/diagnostics/log/xray/access`). They are the built-in OPNsense log pages: full-text search, severity filter (range/exact), history (last day/week/month/no limit), CSV export and a *Flush log* button. The plugin installs the `xraylog.py` format handler into `/usr/local/opnsense/scripts/syslog/logformats/`, so timestamps and severity are parsed; it is removed by `uninstall.sh`. On Apply, the plugin also writes `/var/run/xrayclient-outbounds.json` with the `node_<uuid> → node name` mapping, so the Process column shows the node's human name (e.g. `tun-in -> USA03-up-test`) instead of the raw tag; other tags (`direct`, `auto`, …) show as-is. The access log (and DNS log into the same file, when enabled) carries no severity level: rows are reported as **Informational** and the Process column shows the `inbound -> outbound` detour (or `dns` for DNS answers). Note the diagnostics page defaults to Warning for non-core scopes, so switch the severity dropdown to **Informational** once on the Access Log page — the choice persists in browser storage.
- **Built-in DNS**: switch on **DNS Servers → Enable Built-in DNS** (the settings sit above the resolver table) to resolve domains through Xray instead of the system resolver. The **DNS Servers** tab manages the list - address (`https://1.1.1.1/dns-query` for DoH, `https+local://…` for DoH direct, `tcp://host` / plain IP for Do53, `fakedns`), optional port, domain rules this server serves (`geosite:ru`, `domain:ya.ru`, `domain:ru` suffix rule — works without GeoData, `full:example.com`), answer filters (`expectedIPs` / `unexpectedIPs` as CIDRs or `geoip:` tags) and `skipFallback` (never answer other domains). Add/edit starts from a built-in preset (Cloudflare / Google / AdGuard DoH for all domains, Cloudflare DoH direct (`https+local://`), Yandex DoH / plain DNS for `.ru/.рф/.su` with expectedIPs `geoip:ru` and skipFallback, and the system resolver), the same way as the rule dialog. Servers with no domain list answer everything else; Xray's default server is skipped for requests already matched by a tagged server. Hosts, query strategy (Use IP / IPv4 / IPv6), cache, parallel query, system hosts are set on the same screen (**General Settings → Built-in DNS server**); static `hosts` can also be a raw JSON object. DNS requests follow the same routing rules as ordinary traffic, so unmatched traffic still goes `direct`. The built-in DNS takes precedence over the raw `dns` JSON in the *Raw JSON: dns* row of the Built-in DNS section, which is used only while Built-in DNS is off.
- **Latency/Traffic**: *Check Latency* is a bare TCP connect to each enabled node's address:port (not a full VLESS/REALITY handshake). Traffic counters come from Xray's StatsService (`127.0.0.1:10085`). In **General Settings → Telemetry & Statistics** you can enable background polling: traffic refreshes at the configured interval (30–3600 s), latency is polled every 5 minutes on a separate hardcoded timer. A "Total traffic" summary (↓/↑ across all nodes) is shown next to the refresh button. The Outbound Nodes table then updates automatically instead of only on button click.
- **GeoData presets**: `official` (Loyalsoldier), `runetfreedom` (RU), `zaborona` (Iran-specific, Chocolate4U), `custom` (your `.dat` URLs).
- **Show advanced fields (General tab)**: the General Settings, Balancers and DNS Servers tabs hide rarely edited knobs by default — extra log options, TUN MTU / IPv6 / outbound binding, advanced sniffing and observatory knobs, strict/parallel DNS switches and the raw JSON rows — behind a **Show advanced fields** switch at the top of each tab, the same as in the node dialog; the three switches move together and the choice persists per browser (`localStorage`), independently of the node dialog's toggle.
- **Raw JSON rows**: with *Show advanced fields* on, the *Load Balancer Observatory* section of the Balancers tab and the built-in DNS settings of the DNS Servers tab end with raw JSON rows (*Raw JSON: `routing.balancers`* and *observatory* on Balancers, *`dns`* and *`dns.hosts`* on DNS Servers) that inserts a raw block into the generated config - a top-level `dns` object, `routing.balancers` and an `observatory`/`burstObservatory` object. They apply in UI Builder mode only (Raw JSON mode replaces the whole file), empty fields are omitted, JSON syntax is checked in the browser — the General raw rows, and every raw JSON field of the node dialog (Extra, XHTTP Extra, XDRIVE Extra, Final Mask, Custom Stream JSON, HTTP Headers, Final Rules, DNS Rules: Save is aborted and the offending field is highlighted) — and `xray run -test` remains the final gate on Apply. These are the fallback path: balancers from the **Balancers** tab take precedence over `balancers_json`, an enabled observatory type overrides `observatory_json`, and Built-in DNS overrides `dns_json`. Balancer `selector` matches outbound tags by prefix, so `"node_"` covers every configured node that is a real egress path: the generator expands the prefix into explicit tags and leaves out `freedom`, `blackhole`, `dns` and `loopback` nodes, which a balancer or observatory must never pick. If a prefix matches only such non-proxy nodes, the selector becomes `__none__` (matches no outbound): Xray rejects an empty selector list, and this way the config stays valid while the balancer selects nothing and fails closed.
- **XDRIVE transport** (Xray-core 26.11.9+): a VLESS-only transport that tunnels through a cloud drive instead of a public server port. In the node dialog choose **Transport Network → XDRIVE**, then pick the storage: `google-drive` (OAuth client ID/secret + refresh token and the Drive folder ID), `s3` (endpoint, optional region, bucket, keys, optional session token and path-style addressing for MinIO), `template` (a REST template JSON object, with `{secret0}`, `{secret1}`… substituted from the secrets JSON array) or `local` (a local folder). **XDRIVE Extra** is a JSON object merged into `xdriveSettings` for tuning (`segmentBytes`, `flushIntervalMs`, `pollIntervalMs`, `concurrency`, `eagerWindowMs`, `holeTimeoutMs`, `xmux`, …). Xray requires a non-`none` VLESS **encryption** (generate one with `xray vlessenc`), no VLESS flow, and Mux.Cool enabled with `concurrency >= 0`; the model rejects a node that breaks these rules before saving. For Google Drive also set TLS; use a real Google IP, SNI `www.google.com`, ALPN `h2` (or `h3` alone for QUIC) and fingerprint `hellochrome_155`/`chrome`; the client and server must run the same Xray version. There is no standard share-link representation for `xdriveSettings`, so a `vless://…type=xdrive` link only selects the transport — fill in the storage fields manually.
- **Link import schemes**: `vless://`, `vmess://` (base64 JSON), `trojan://`, `ss://` and `hysteria2://` / `hy2://`. `type=raw` is TCP, `insecure=1` / `allowInsecure=1` ticks *Allow insecure*. A Hysteria 2 link fills the auth string, SNI and Allow insecure; `obfs=salamander` with `obfs-password` becomes the Salamander mask of FinalMask UDP, `mport` becomes a UDP Hop mask (mode `intervalremote`, 30 s, the ports of the link; the server IP goes into Remote IPs when the link has one, otherwise the notice asks for it), both together are written to the raw FinalMask field as a chain (Salamander first), and `pinSHA256` (hex with or without colons) fills the pinned certificate field. The remote hop modes need the matching iptables/nftables redirect on the server, as in Xray's own documentation. A VMess link fills the UUID, transport (tcp, ws, grpc, xhttp, httpupgrade), TLS, SNI, ALPN and security; unsupported transports, alterId other than 0 and header types are reported.
- **Link import notes**: the remark of a link becomes the node name, but the name accepts only letters, digits, spaces and `. _ - ( ) [ ] @ # / & ! + : ; , "`, so flags, emoji and other scripts are dropped (the address stands in for a name that is left empty). The `fm=` parameter (FinalMask JSON) is imported: a single TCP `fragment` with `tlshello` or `1-3` fills the FinalMask rows, anything else (chains, other types, UDP, QUIC tuning) goes into the raw FinalMask field. Parameters the dialog cannot take are listed in a notice at the top of the dialog: a fingerprint that is not among the options (the node keeps `chrome`) and `cs` (cipher suites, no such field).
- **uTLS fingerprints**: the Stream Security fingerprint list exposes the versions added in recent Xray releases — `hellochrome_155` (also the target of the `chrome` preset), `hellochrome_133/131/120`, `hellofirefox_148/120`, `hellosafari_26_3`, `helloios_14/13`, `helloedge_106`, `hello360_11_0`, `helloqq_11_1`, plus the `360`, `qq` and `randomizednoalpn` presets. Older Xray builds reject unknown names, so keep the core updated when selecting the newest ones.
- **FinalMask**: the node dialog configures one mask per direction as ordinary rows. *FinalMask — TCP* offers `fragment` (packets — a dropdown with the two modes, `1-3` cuts the TCP flow on the 1st-3rd write operation of the client, `tlshello` fragments the TLS Client Hello — lengths, delays, max splits), `sudoku` (password, ASCII table, padding, custom tables) and `header-custom`/`xmc`; *FinalMask — UDP* offers `salamander`, `gecko` (Salamander with packet fragmentation, min/max packet size), `sudoku`, `udphop` (mode, interval, remote IPs/ports), `mkcp-legacy`, `xicmp`, `realm` and `noise`/`xdns`/`header-custom`; *FinalMask — QUIC Parameters* covers congestion control, BBR profile, Brutal rates, idle timeout, KeepAlive, incoming streams, the four receive windows and Path MTU Discovery. `fragment` lengths and delays use the OPNsense tokenizer (like the alias *Content* field): type a size or range and press Enter or comma to make a tag, with *Clear All*, *Copy*, *Paste* and *Text* below the field, e.g. `3-7`, `4-9`, `6-9` and `30-40`, `40-50`; every Int32Range value (`maxSplit`, `interval`, `packetSize`...) is emitted as a string. The UDP masks are also shown for the *Hysteria* protocol — its stream is QUIC over UDP, so the mask applies to the tunnel: `salamander` (password), `gecko` (password + packet size or range in bytes, max 2048; the mask is emitted as `type: salamander` with `packetSize`, which is how the core represents Gecko) and `sudoku`. Types whose settings are nested arrays (`header-custom`, `noise`, `xdns`, `xmc`) take them as a JSON *settings* object. The old **Raw FinalMask JSON** row is still there and wins whenever it is not empty, which is also the only way to chain several masks — `finalmask.tcp` and `finalmask.udp` are arrays and the first entry is the innermost layer. Xray-core 26.11.9 reads `udphop` as `mode`/`interval`/`remoteIPs`/`remotePorts` and `xdns` as `domains`/`resolvers`; keys written for older cores (`sockopt` in `udphop`, `domain` in `xdns`) are ignored without any error from `xray run -test`, so verify the obfuscation on a live connection. The save-time checks mirror the core limits: UDP Hop interval ≥ 5, Salamander packet size ≤ 2048, QUIC idle timeout 4-120, KeepAlive 2-60, incoming streams ≥ 8, receive windows ≥ 16384, and Force Brutal requires an upload rate. TCP masks are offered only for TCP-based transports; UDP masks and the QUIC parameters only for QUIC-based ones (Hysteria, MASQUE over HTTP/3 - no `h2` in ALPN - and XHTTP with `h3` in ALPN), and the config keeps just the matching kind. *UDP Hop Mode* is a multi-select; the remote modes require Remote IPs and Remote Ports. FinalMask is written into `streamSettings.finalmask` for every protocol (older plugin builds wrote it one level up for VLESS/VMess/Trojan/Shadowsocks-style outbounds, where the core ignored it).
- **TLS trust options** (node dialog, TLS security): **Use System CA Store** (`useSystemCA`, Xray-core 26.11.9+) makes Xray trust the operating system's CA list instead of its built-in one, for servers signed by a private CA installed on the router. It is off by default and shown under *Show advanced fields*. **Allow Insecure TLS** is deprecated in Xray-core: for a self-signed server pin its certificate with **Pinned Peer Cert SHA-256** instead (`xray tls hash` / `xray tls ping` print the value); the option still works but may disappear from a future core.
- **Maintenance**: *Maintenance* shows installed Xray-core / GeoData / plugin versions and a **Check for Updates** button that queries GitHub for the latest Xray-core release and the latest plugin commit (it needs outbound HTTPS to github.com). From there you can update Xray-core or the plugin itself in one click. **Plugin Branch** picks which branch of the repository "Update Plugin from GitHub" installs: `main` by default, or any unmerged branch to try changes before they are released (the list is read from GitHub when the tab opens; if GitHub is unreachable you can type the branch name by hand). A non-`main` branch is marked with a warning and the button changes to *Install Plugin from branch …*, because its code runs as root; after a plugin update the service is restarted automatically, but only if it was running and the regenerated config passes `xray run -test`.
- **Live traffic**: the **Live** switch on the Outbound Nodes tab shows per-node rates (sampled every 5 s, only while that tab is open); the dashboard widget has the same option with a 2–30 s interval. Every sample queries Xray's stats API on the router.
- **Input validation**: raw JSON node fields (VLESS/XHTTP/XDRIVE extra, FinalMask, custom stream, HTTP headers, Freedom final rules, DNS rules) must be valid JSON of the right kind and at most 8192 characters; the XDRIVE transport is offered only for VLESS. Node fields that are critical for Xray are validated on save — WireGuard keys (44 base64 chars), endpoints (`host:port`), SNI/host/path formats, JSON fields (`http_headers`, `custom_stream_json`, `freedom_final_rules`, `dns_rules_json`), CIDR lists and MTU/keepalive/timeouts. Invalid values are rejected with a message before the config is written; `xray run -test` is still the final gate on Apply & Restart.
- **WARP (Cloudflare)**: in the WireGuard section of the Add/Edit node dialog, click **Generate WARP config** to create a local WireGuard keypair, register with Cloudflare's WARP API, and auto-fill all WireGuard fields (private key, server public key, endpoint, allowed IPs, DNS, MTU, keepalive, reserved bytes). Requires outbound HTTPS to `api.cloudflareclient.com`. If registration is unreachable, public WARP fallback values are used instead — you may still need to register via the WARP app/website for a working connection. API version and fallback values can be overridden via optional `/usr/local/etc/xray/warp.json` (must be a JSON object with keys like `api_version`, `registration_urls`, `fallback_public_key`, `fallback_endpoint`, `fallback_allowed_ips`, `fallback_dns`, `fallback_mtu`).
- **WARP over MASQUE** (Xray-core 26.11.9+, node dialog → protocol **MASQUE**): set **MASQUE Mode** to *Cloudflare WARP* to use the built-in WARP client of the core instead of a custom CONNECT-IP server (the authority, path, credentials, headers and remote DNS rows disappear). MASQUE runs inside TLS over HTTP/2 (or HTTP/3), which helps where UDP/WireGuard is blocked or throttled. It needs a **P-256 device key** and the addresses of a device registered *with MASQUE support* (`warp_enabled`); the WireGuard keys of `wgcf` / **Generate WARP config** do not work. **Generate WARP config** registers a new free WARP device for you: it creates a P-256 key on the router, registers the device with Cloudflare, enrolls the key for MASQUE and fills the private key, the edge public key, the device addresses and the endpoint (the same steps as `usque register`, see [usque](https://github.com/Diniboy1123/usque), MIT, whose protocol description this follows; it needs outbound HTTPS from the router to `api.cloudflareclient.com`, nothing is saved before you press Save). The API version and client headers are built in and can be overridden in `/usr/local/etc/xray/warp.json` (`masque_api_base`, `masque_client_version`, `masque_user_agent`) if Cloudflare changes them. WARP+ and Zero Trust licenses are not bound by this button; register such a device with usque (`usque register`) and paste its `config.json` into **Import from usque config**, which fills the same fields. Or fill the three fields by hand (*WARP Private Key* as base64 DER without PEM header lines, *WARP Edge Public Key*, *WARP Device Addresses*). **Endpoint for account type** sets the endpoint address (WARP `162.159.198.2`, WARP+ `162.159.199.2`, Zero Trust `162.159.197.2`, port 443), the SNI `consumer-masque.cloudflareclient.com` and the `h2` ALPN when they are empty; other ports such as 500, 1701, 4443, 4500 or 8443 work too if 443 is blocked. **Fetch edge key** reads the endpoint's certificate from the router and fills *WARP Edge Public Key* (the guide's `openssl s_client ... | openssl x509 -pubkey` command; it needs outbound access from the router to the endpoint). The key belongs to the endpoint IP, so fetch it again after changing the address. Instead of the edge key you can pin the certificate with *Pinned Peer Cert SHA-256* or *Verify Peer Cert By Name*; the edge key is then ignored. ECH is not supported by the MASQUE edge. For HTTP/2 the *FinalMask - TCP* fragment of the TLS ClientHello (`tlshello`) is the recommended obfuscation, for HTTP/3 (`h3` in ALPN) use a UDP mask such as `noise`. Routing and proxy chains work as for the WireGuard WARP node.
- **Find working endpoint** (WireGuard WARP nodes and MASQUE nodes in WARP mode): when the default WARP endpoint is blocked, the button searches for endpoints that work from this router. Progress and results open in their own window above the node dialog (progress bar, a table of every checked endpoint with *Use* and *Re-check*, *Re-check all*, *Cancel search*); closing the window does not stop the search, and the *Results* link next to the button reopens it. The ranges and ports come from the community list of WARP endpoints ([Cloudflare WARP endpoints](https://help-guide.notion.site/Cloudflare-WARP-1f82684dab0d8024a1c8fec230f5e4e1): 14 address ranges and 54 ports for WireGuard, `162.159.198.x` / `162.159.199.x` with ports 443, 500, 1701, 4500, 4443, 8443, 8095 for MASQUE; the Zero Trust ranges `162.159.193.1-10` and `162.159.197.1-10` only with the *Zero Trust ranges* option). The documented addresses are tried first but get no special trust. A candidate is tested for real: a temporary Xray (127.0.0.1 only, no TUN, WireGuard with `noKernelTun`) uses the keys currently entered in the dialog and the candidate as its endpoint, and has to fetch Cloudflare's `/cdn-cgi/trace` with `warp=on` (or `plus`) from an address different from the router's own. A candidate that passes is **confirmed** before it is called *verified*: three more trace requests and a 300 KB download through the same instance must succeed; a candidate that answers but fails part of that is shown as *unstable*, and a lucky single answer is never accepted. The search takes random addresses and ports round-robin over the ranges, so one blocked range does not use up the budget, and stops after the wanted number of verified endpoints (default 5) or the attempt limit (default 80). Failed endpoints are not retried for 6 hours (option to retry them anyway); verified ones are kept on the router (`/usr/local/etc/xray/warp_probe_cache.json`, no keys) and shown with their age. **Re-check** repeats the full confirmation for one endpoint, **Re-check all** for the whole list, and endpoints that no longer pass drop out of the saved list. **Use** fills the endpoint into the dialog (for MASQUE also the ALPN of the chosen mode and, for HTTP/2, the edge key read from that address); nothing is saved until you press Save. In MASQUE mode choose HTTP/2 (TCP, a quick TLS pre-check first) or HTTP/3 (UDP). WireGuard probes do not use FinalMask. The test needs the router's own traffic to leave through the WAN. For MASQUE the follow-up requests run at the same time, and MASQUE results carry the debug log of the temporary Xray (*Log* button). If the tunnel comes up and the first request goes through WARP but later flows never get an answer (seen with Xray 26.11.9), the candidate is shown as *unstable* with the note *tunnel up, later requests stalled*. For MASQUE the option *Apply this node's FinalMask* (on by default) sends the probe the way the node would, with the FinalMask rows of the dialog (TCP fragment, Sudoku and custom masks for HTTP/2, Salamander, Gecko, Sudoku and custom masks for HTTP/3, or the raw FinalMask JSON): where the connection is filtered, a probe without the mask can get its first request through and stall afterwards. Each result shows a country flag before the address; the tooltip names the city, the country and the Cloudflare data center that answered. The data center comes from the trace of the probe (`colo`), so the flag tells where the traffic of that endpoint comes out, not where the address is registered (the addresses are anycast). The list of data centers is fetched by the router from `speed.cloudflare.com/locations`, kept for a week, with a short built-in table as the fallback. Browsers on Windows draw flag emoji as two letters. Only Cloudflare-style IPv4 addresses are tested; the keys travel from the dialog to the script in a private temporary file. **External lists** (WireGuard mode, option *Use external lists*, off by default and remembered in the browser): the built-in ranges are static, so Maintenance → *WARP Endpoint Lists* takes up to 10 `https://` URLs of community lists (default: the `warp-endpoints-collector` `result.json`; the address is not verified by the plugin, replace it if the list moves). Accepted formats: JSON list of `{"ip": ..., "ports": [...]}`, an `ip → ports` object, `ip:port` strings, or plain text/table rows. Entries are tried right after the documented addresses and before random sampling, but are tested like any other candidate, so a list is never trusted. Lists are downloaded by the router (https only, 2 MB limit), cached for 24 hours and an old copy is used if the download fails. **MASQUE** has no published list of endpoints, so with *Use external lists* the addresses of the same lists are tried on the MASQUE default port 443 (the ports in the lists are WireGuard ports and are ignored), and *Also try other WARP ranges* (experimental) adds `162.159.192.x`, `162.159.195.x` and the WireGuard ranges to the sampling with the MASQUE ports; whether anything answers there is decided by the same test, so expect more failed attempts than in the default ranges. Only Cloudflare ranges are tested unless *Also test addresses outside Cloudflare ranges* is ticked; the status line shows how many entries were used, skipped or could not be loaded.

## Uninstall

```sh
sh /tmp/os-xray-client-main/uninstall.sh
```

This removes the plugin files. The Xray binary, GeoData and `/usr/local/etc/xray/config.json` are kept for a future reinstall — remove them manually if you want a fully clean box.

## Development / Git

Files are LF-only (see `.gitattributes`). On Windows, keep `git config core.fileMode false` so the executable bits (`755`) of scripts aren't lost; `install.sh` also re-applies `chmod +x` on the firewall.
